# Remora: a native macOS viewer for the reMarkable cloud — design

**Date:** 2026-10-21
**Status:** Agreed with the user decision by decision (Q1–Q36 of the design
interview). The implementation plan comes next.
**Builds on:** rm2agent (`gveres/rm2agent`). Its cloud, page-map and rendering
findings are restated here so this repo stands on its own.

## Goal

A Mac app for browsing a reMarkable account through the cloud, built for
reading. Every document, folder and page has a stable `rmr://` link that
opens it directly in the app. An open notebook updates by itself while
someone writes on the tablet. A small set of library writes is included:
rename, new folder, move, upload, trash. Ink is never edited.

The name: a remora is the fish that rides along on something bigger.
`rmr` is "remora" without its vowels.

## Decisions

| Decision | Choice |
| --- | --- |
| Platform | Native Swift/SwiftUI, macOS 26+, **not sandboxed**. Personal build first; later notarized and distributed as a DMG |
| Licence and hosting | MIT. `gveres/remora`, private until v1 |
| Identity | App **Remora**, bundle ID `io.github.gveres.remora`, URL scheme **`rmr://`**. `remora://` is already taken by the remora-sh SSH client |
| Structure | `RMKit`, a Swift package (cloud, parser, page map, render, cache) tested with `swift test`, plus a thin app target generated by XcodeGen (`project.yml`, no hand-edited `.xcodeproj`) |
| Stack | All Swift. Port the read and write cloud client, the `.rm` parser and rm2agent's flat renderer. Use PDFKit for PDF and EPUB pages, with Core Graphics drawing the ink on top |
| Transport | Cloud only: sync v3/v4 root-hash protocol plus the notification websocket. No USB web UI, SSH or LAN |
| Accounts | Several from day one. Each is paired separately, keeps its device token in Keychain, and is labelled with the email from its session token. Each account has its own cache and sync loop |
| Scope | Folders, notebooks, PDFs and EPUBs with ink and highlights, tags and pins (as filters). An EPUB is shown as the PDF the tablet renders beside it. Out: trash view, version history |
| Writes | Rename, new folder, move (drag and drop), upload PDF/EPUB (drag from Finder or the menu), move to trash. Out: permanent delete, emptying the trash, editing tags and pins, anything touching ink |
| Write UX | Applied immediately, with no confirmation dialogs. Cmd-Z applies the inverse operation, and undo history lasts until the app quits. A failed write shows an error and puts the cloud's state back on screen. Writes are disabled while offline, with no queue |
| Links | `rmr://doc/<docUUID>`, `rmr://doc/<docUUID>?page=<pageUUID>`, `rmr://folder/<folderUUID>`. They carry no account or names; the app finds the account by looking the UUID up in every account's index. Only the user opens them, so there is no https or universal-link form |
| Windows | One library window (sidebar tree, list or grid, search) and one window per document. A link opens or focuses the document's window and scrolls it to the page. macOS window tabbing provides tabs |
| Library | List view by default (name, modified, type, pages), built from the index alone. The grid view renders a first-page thumbnail only when the item scrolls into view, then caches it |
| Search | Titles, tags and folder path, from the cached index. Cmd-F inside a PDF or EPUB uses PDFKit's find. Out: typed-text search across the library |
| Document view | Continuous vertical scroll, thumbnail sidebar, fit-width by default, pinch or Cmd +/− to zoom. PDF text and typed notebook text can be selected and copied. Landscape pages are rotated correctly |
| Live view | Notification socket, with a root-hash poll every 30 s as a fallback. Only changed pages are refetched and redrawn. Scroll position and zoom stay put, changed thumbnails flash, and a "jump to latest edit" button appears |
| Rendering M1 | Flat ink, ported closely from rm2agent's `strokes.ts`, `palette.ts` and `geometry.ts`: width follows pressure, highlighter and shader are translucent, the palette is the same |
| Rendering M2 | Textures for pencil, mechanical pencil and paintbrush only. The grain is generated in code, seeded per stroke and fixed to the page. Every constant lives in one per-pen table, tuned by eye. "Plain ink" stays available as a preference and is always used in tests |
| Templates | The lines, grid and dots families (small, medium and large) and Blank are drawn as geometry. Any other template name shows a blank page with a "template: X" badge |
| Copy and share | Copy Link (Cmd-L), Copy as Markdown Link (`[Title p.12](rmr://…)`), Copy Page as Image (PNG). The toolbar Share button offers the document as a PDF plus its link; Share Page offers a PNG |
| PDF export | Export PDF… (Cmd-Shift-E) and the Share button. Ink is always flat vectors: over the drawn template for a notebook, over the original PDF for a PDF or EPUB, so its text stays selectable. Exports the whole document or the current page |
| Cache | Content-addressed, under `~/Library/Caches/Remora/<account>/`. Least recently used is evicted once it passes 2 GB (configurable). Entry lists and the index are never evicted. Cached content can be browsed offline, and the app shows when it last synced |
| Lifecycle | Syncs only while the app is running. No menu-bar agent, login item or daemon. A link opened while the app is closed launches it, shows the cached copy, then refreshes |
| Tests | Committed fixtures are rmscene's MIT-licensed samples (with their goldens) plus, later, a purpose-made fixtures notebook and PDF on the tablet; never content from the user's own library. ### Rejected

- **Links readable by other people** (a server-backed https link): that is a
  hosted product with access control. Links are for the user only.
- **An https universal-link form**: it needs a domain and associated
  domains, for slightly nicer links.
- **A direct USB or SSH connection to the tablet** for faster live updates: a
  second transport that breaks with every firmware update.
- **A Node sidecar running rm2agent's code**, or **rmapi-js embedded in
  JavaScriptCore**: two runtimes forever, or a lot of polyfill work in
  JavaScriptCore (no `fetch`, no Node crypto).
- **Reusing rm2agent's `~/.rm2agent/auth.json`**: it couples the app to
  rm2agent's file layout, and that file stores the token as plain JSON.
- **The account in the URL**: UUIDs are already globally unique.
- **Strictly read-only**: dropped at the user's request. The writes are
  limited to library operations.
- **Confirmation dialogs**: undo is enough, and trash can be restored from
  the tablet.
- **Follow mode** for live edits: possible later as a toggle.
- **Tilt shading**: no file format since v3 stores tilt (see below).
- **GPL textures** (rmrl, RCU, remy) and **firmware assets**: copying them
  would make the app GPL or redistribute reMarkable's files.
- **An import folder for the tablet's own template images**: the user chose
  geometry only.
- **Textured PDF export**: grain drawn as vectors bloats files. Textures
  appear on screen and in PNGs only.
- **"reMarkable" in the name**: it is a trademark, and the app is meant to
  be open source.

## Cloud protocol (from rm2agent, verified on the user's account)

**Hosts and auth.**
- Auth host: `https://webapp-prod.cloud.remarkable.engineering`.
  - Pairing: `POST /token/json/2/device/new` with the one-time code from
    `my.remarkable.com` returns a device token. It never expires and goes in
    Keychain.
  - Session: `POST /token/json/2/user/new` with `Bearer <deviceToken>`
    returns a session JWT that lasts about a day. It is never written to
    disk.
- The session JWT carries `auth0-profile` (`Email` and `Name`, used for the
  account label), `level` (e.g. `"connect"`) and `tectonic` (e.g. `"eu"`).
  `tectonic` picks the sync host, `https://<tectonic>.tectonic.remarkable.com`.
  rmapi-js hardcodes `eu`, so non-EU accounts have to be handled.
- The token exchange is rate-limited and answers 429. **Keep one long-lived
  session per account**, retry once on 401, and refresh the session before
  it expires.
- 402 or 403 means the account has no Connect subscription. Show that
  clearly rather than as a generic error.

**Sync tree.**
- One root hash with a numeric generation. The root's entry list uses
  schema 4; each document's entry list uses schema 3. Every blob is
  addressed by its hash, which is why the cache never has to invalidate
  anything.
- Each document's entries are `.metadata`, `.content`, `<pageUUID>.rm` per
  inked page (a page with no ink has no file), and `.pdf`, `.epub` or
  `.pagedata` where they exist.
- Index fields: `id`, `hash`, `visibleName`, `parent` (`""` is the root,
  `"trash"` the trash), `pinned`, `tags`, `lastModified`, `lastOpened`,
  `fileType` (`pdf`, `epub` or `notebook`).
- Re-read the root hash every time. A long-lived client that caches it sees
  a frozen account.
- Cost on the user's account: 545 entries, about 25 MB of entry lists, a
  cold listing in 3–5 s. With the content-addressed cache, only lists whose
  hash changed are fetched again. Limit concurrent blob fetches.
- Change detection: compare the root hash, then each document's `hash`, then
  each page file's hash. That gives exactly the pages to redraw.

**Writes.**
- A write uploads the new blobs, then commits with `putRootHash(hash,
  generation)` as a single root update.
- A generation conflict means re-read, rebuild the change on top, and retry,
  up to 3 times.
- Write the entry lists the way the desktop app does (schema 3 per document,
  schema 4 at the root), which matches rm2agent's mitmproxy capture.
- A freshly uploaded PDF reports 1 page until the tablet opens it.

**Notifications.**
- `wss://<tectonic>.tectonic.remarkable.com/notifications/ws/json/1`, with
  `Authorization: Bearer <sessionJWT>` on the handshake
  (`URLSessionWebSocketTask`). Messages only flow from server to client.
- Frame: `{"message":{"attributes":{"event":"SyncComplete","sourceDeviceID",…},…}}`.
  Keep only `SyncComplete`, and skip events whose `sourceDeviceID` is our
  own device. An event never says what changed, so it is only a signal to
  re-read the root hash.
- The server closes the socket every few minutes. Reconnect with backoff
  from 1 s up to 60 s, and reopen it every hour regardless, because a dead
  socket looks exactly like a quiet account. The 30 s root-hash poll covers
  the gaps.
- **Latency ceiling:** while a document is open, the tablet commits its ink
  about **once a minute**, and again on close (rm2agent's concurrent-ink
  spike, 2026-10-01). The notification follows about 1 s later. So "live"
  means updates arrive in chunks about every minute.

## Content model

**Page order and IDs.** The `.content` file uses one of two schemas. Detect
which one by its shape, not by `formatVersion`:
- **Legacy:** `pages[]` (page UUIDs in order) plus `redirectionPageMap`
  (pointing at source PDF pages).
- **New:** `cPages.pages[]`, ordered by the fractional index `idx` compared
  **byte-wise**. It has optional `redir` (the source PDF page, zero-based)
  and `deleted` flags. Pages flagged `deleted` stay in the list and **must
  be filtered out**, or every later page number shifts.

The page UUID stays the same when pages are inserted or reordered. Links
therefore key on the page UUID, and page numbers are always derived. Quirks:
- `pages` is `null` on a never-opened document.
- A `formatVersion: 2` notebook can have `pages: []`. Fall back to
  document order.
- PDFs uploaded through rmapi-js keep the legacy schema even after they are
  annotated.

**Templates.** The template name is in `cPages.pages[].template.value`, or
in `<docid>.pagedata` (one name per line, in page order) for older
notebooks. Accounts use both, so read both. Built-in template images live
only in the tablet's firmware. Names in the user's account include
`P Lines medium`, `P Grid medium`, `P Dots large` and `Blank`.

**Ink: per-point data.**
- **v6, current format (14 bytes):** `x` and `y` are float32 device pixels
  with the origin at the centre. Then `speed` u16, `width` u16 (×4 compared
  with the old float format), `direction` u8 (0–255 maps onto 0–2π), and
  `pressure` u8 (0–255).
- **v6, older format (24 bytes):** six float32 values, rescaled the way
  rmapi-js does it: speed ×4, direction ×255/2π, width ×4, pressure ×255.
- **v3 and v5:** six float32 values: x, y, speed, direction (radians),
  width, pressure (0–1).
- **`direction` is the heading of the stroke, not the pen's tilt.**
  Measured on rmscene samples, it deviates from `atan2(dy, dx)` by 8–14° on
  average, where random values would give 90°. No format since v3 stores
  tilt; whatever the tilt does is already folded into `width`.

**Pages, pens and colours.**
- Page geometry: **each page** has its own screen size. 1404×1872 and
  1620×2160 both appear, even within one document. Orientation, by contrast,
  is a document-level fact from `.content`; no page carries it (measured on
  rm2agent).
- v6 layers can be hidden, and eraser strokes are dropped from rendering.
- Pen codes:

  | Pen | Codes |
  |---|---|
  | brush | 0, 12 |
  | pencil | 1, 14 |
  | ballpoint | 2, 15 |
  | marker | 3, 16 |
  | fineliner | 4, 17 |
  | highlighter | 5, 18 |
  | eraser | 6 |
  | mechanicalPencil | 7, 13 |
  | eraseArea | 8 |
  | calligraphy | 21 |
  | shader | 23 |

- The palette is ported from rm2agent's `palette.ts`. A highlight stroke
  uses its own `colorRgba`. **Pen and colour lookups are exhaustive**, so a
  code we don't know fails loudly in tests rather than silently rendering
  black.

**Typed text.** v6 text is a CRDT. It is ordered by a topological sort,
mirroring rmapi-js and rm2agent's `text.ts`. If the order is ambiguous,
show the text as unordered rather than guess.

**PDF highlights.** They come from the document's highlight files, and the
text of each one is joined in reading order (rm2agent's `joinHighlights`).

## Rendering

**Milestone 1, flat ink.**
- The `.rm` parser is a hand port of rmscene (MIT), checked against rmapi-js
  wherever they differ. Attribute rmscene in the source.
- Stroke normalization ports rm2agent's `strokes.ts`: one list of strokes in
  page coordinates, a single width model, pressure from 0 to 1.
- Each stroke is drawn with Core Graphics as runs of segments whose width
  varies.
- **Golden check:** render the same pages with rm2agent's `export --format
  svg` and with RMKit, then compare the SVG text byte-for-byte, not a
  rasterised comparison. Fixture pages are committed; pages from the real
  library run locally only.

**PDF and EPUB.**
- PDFKit draws the page, and the ink layer sits on top in PDF points
  (rm2agent's `pdf-transform.ts` mapping). It accounts for the page box and
  `/Rotate`.
- **Known bug to fix, not port:** on a 1620×2160 pt PDF, the tablet stores
  ink as PDF points × 226/72 with x centred. rm2agent's export assumes the
  page is fitted to the 1404 px screen, so the ink lands off the page. The
  large-format fixture PDF covers this case.

**Milestone 2, textures.**
- **Pencil:** dense grain. Dots are scattered with blue noise, and their
  density follows pressure. Speed thins the stroke.
- **Mechanical pencil:** the same grain, lighter.
- **Paintbrush:** streaky, ragged edges. Darkness follows pressure and
  speed, and the streaks align with `direction` (the heading).
- **Other pens** stay solid.
- **Starting values:** rmc's per-pen width and opacity formulas (MIT, ported
  with attribution). They treat `direction` as tilt, which it isn't, so
  re-fit those terms. The GPL renderers (rmrl, RCU, remy) are a source of
  ideas only.
- **Determinism:** the noise is seeded from the stroke's CRDT ID on v6. v3
  and v5 have no stroke IDs, so the seed is the page UUID plus the stroke's
  index; those files don't change live anyway. A live redraw puts the same
  dots in the same places. The grain is fixed to the
  page and scales with zoom, like paper.
- **Tuning:** all constants live in one per-pen table. They are tuned by eye
  against photos of the fixtures' textured-pens page, written at light,
  medium and heavy pressure, or captures from the desktop app.

## App structure

**RMKit modules** (folders in one package until there is a reason to
split):
- `Cloud`: auth, session, root and entries, blobs, writes, notifications.
- `Cache`: content-addressed store with LRU eviction.
- `Model`: index, tree, page map, templates, text.
- `Parse`: `.rm` v3, v5 and v6.
- `Render`: strokes, palette, geometry, flat renderer, textures, templates,
  PDF overlay, PDF export.

**App.**
- An account store backed by Keychain.
- One sync actor per account: session, socket, poller and index.
- The library window and the document windows.
- A URL handler for `rmr` (`CFBundleURLTypes` plus `.onOpenURL`) and a
  resolver that looks a UUID up across accounts.
- Pasteboard, `NSSharingServicePicker`, export and settings: accounts,
  cache size, Plain ink.

**Link resolution.**
- Look the UUID up in each account's cached index first.
- If it isn't there, refresh every account's index.
- Still missing: report "not found". In the trash: say the document is in
  the trash.
- If the `page` UUID is gone, open the document and note that the page was
  deleted.

## Milestones

**M0: setup.**
- **User task:** create the fixtures on the tablet. A notebook with every
  pen and colour, a landscape page, typed text, every template family and a
  textured-pens page at three pressures. Also a large-format (1620×2160 pt)
  annotated PDF and an annotated EPUB.
- Repo scaffolding: SwiftPM, XcodeGen, an `rmr` scheme stub that logs the
  URL it received.

**M1: the viewer, flat ink.** Suggested build order, each step usable on
its own:
1. RMKit cloud read path: pairing, Keychain, session, root and entries,
   blobs, cache. A command-line smoke test lists the account.
2. Parser and flat renderer, plus the golden check against rm2agent.
3. Library window: tree, list view, search, multiple accounts.
4. Document window: notebooks, templates, PDF and EPUB overlay, selectable
   text, zoom.
5. `rmr://` links, Copy Link and Markdown link, link resolution.
6. Live view: socket, poll, per-page redraw, change markers.
7. Writes, each with undo.
8. Copy and Share Page as PNG, the Share button, PDF export (including the
   large-format fix).
9. Grid view with lazy thumbnails, offline mode, and the "last synced"
   indicator.

**M2: textures.** Pencil, mechanical pencil and brush, the per-pen table,
the Plain ink preference.

**Later.**
- rm2agent prints `rmr://` links in its search, list and recent output.
- Follow mode for live edits.
- Typed-text search across the library, from the cache.
- Rendering Methods templates (JSON DSL).
- Notarization, a DMG release script, and making the repo public.

## Open questions and risks

- **The v6 parser port is the biggest risk.** No mature Swift
  implementation exists; SwiftRm calls itself "very early stages". rmscene
  and rmapi-js are the references, and the golden check is the safety net.
- **Is the region in the token enough?** The `tectonic` claim appears to
  pick the region, but this is verified only on an EU account. Non-EU
  accounts may need an override setting.
- **Two clients sharing one account.** rm2agent and Remora each hold their
  own session per device. Whether the token-exchange 429 limit applies per
  device or per account hasn't been measured.
- **`deviceDesc` at pairing** is a fixed list in rmapi-js (`desktop-macos`,
  `desktop-windows`, …, `browser-chrome`). Remora registers as
  `desktop-macos`. **Verified 2026-10-21:** pairing as `desktop-macos` with a
  code from `my.remarkable.com/device/desktop/connect` works. Whether it
  costs a desktop-app slot (or signs the official desktop app out) is still
  unobserved.
- **How firmware 3 draws pencil.** The only official reference found shows
  1-bit stipple (firmware 2.x). M2 tuning should treat photos of the user's
  tablet as the truth.
- **A Keychain item paired with `remora-cli` is owned by that binary, not
  the app.** macOS ties Keychain access control to the signing identity of
  the process that created the item, so the signed Remora app will prompt
  once to read a device token the unsigned (or differently signed)
  developer CLI stored.
